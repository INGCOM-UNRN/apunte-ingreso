<!-- _header: '¿Qué son?' -->

# Pruebas de Escritorio

**Definición:**
* Ejecutar el algoritmo "a mano"
* Como si fueras la computadora
* Paso a paso, con datos reales

**¿Para qué?**
* Encontrar errores ANTES de programar
* Verificar que la lógica funciona
* Entender mejor tu algoritmo

<!--
Este slide introduce el **concepto fundamental** de pruebas de escritorio.

**¿Qué son las pruebas de escritorio?**

Imaginate que sos la computadora. Vas a "ejecutar" el algoritmo manualmente, siguiendo cada instrucción al pie de la letra, y anotando el valor de cada variable en cada paso.

**Analogía clave:**
"Es como ser un actor ensayando una obra de teatro. Lees el guión (pseudocódigo) y actúas cada escena, asegurándote de que todo tiene sentido antes del estreno (programar)."

**Ejecución "a mano":**
- No usamos la computadora
- Usamos papel y lápiz (o pizarra)
- Simulamos ser el procesador

**"Como si fueras la computadora":**
- La computadora es literal: hace EXACTAMENTE lo que le decís
- No asume, no adivina, no "interpreta"
- Vos también tenés que ser literal en la prueba

**"Paso a paso":**
- Una instrucción a la vez
- Actualizás variables después de CADA operación
- No saltés pasos

**"Con datos reales":**
- No probás con "cualquier número"
- Elegís casos específicos (ej: 5 y 3, no "a y b")
- Usás números que revelen errores

**¿Para qué sirven?**

1. **Encontrar errores ANTES de programar:**
   - Error en papel: 2 minutos corregir
   - Error en código: 2 horas debuggear
   - ROI: 60x más eficiente

2. **Verificar que la lógica funciona:**
   - ¿El resultado es correcto?
   - ¿Cubre todos los casos?
   - ¿Termina el lazo?

3. **Entender mejor tu algoritmo:**
   - Al ejecutarlo, entendés qué hace realmente
   - Detectás optimizaciones posibles
   - Aprendés de tus errores

**Estadística motivacional:**
Estudios muestran que 70% de los bugs se originan en errores lógicos, no sintácticos. Las pruebas de escritorio detectan errores lógicos.

**Pregunta retórica:**
"¿Preferirías detectar un error en 5 minutos con papel, o en 2 horas peleando con Python?"

**Historia real:**
En la NASA, antes de subir código a una sonda espacial (donde no pueden debuggear), hacen pruebas de escritorio exhaustivas. Si funciona para la NASA, funciona para nosotros.

**Objeción común:**
"Pero me parece lento hacer esto para cada programa."

Respuesta: Al principio sí, parece lento. Pero:
- Con práctica, se vuelve rápido (5-10 min)
- Solo lo hacés para algoritmos nuevos/complejos
- Te ahorra mucho más tiempo después

**Conexión con debugging:**
Las pruebas de escritorio SON debugging, pero en la etapa de diseño. Es debugging preventivo, no reactivo.

**Siguiente:** Veremos el proceso concreto de 4 pasos para hacer pruebas de escritorio.

## Ahorra tiempo y frustraciones

<!--
Este slide es un **separador motivacional** entre la introducción y el contenido técnico.

**Mensaje central:** Invertir tiempo en pruebas de escritorio es inversión, no gasto.

**Narrativa:**

Imaginate dos estudiantes:

**Estudiante A:**
1. Escribe pseudocódigo (10 min)
2. Programa directamente en Python (15 min)
3. Ejecuta, no funciona
4. Debuggea durante 2 horas
5. Encuentra el error: un `<` debía ser `<=`
6. **Total: 2h 25min, muy frustrado**

**Estudiante B:**
1. Escribe pseudocódigo (10 min)
2. Hace pruebas de escritorio (10 min)
3. Detecta el error del `<` vs `<=`
4. Corrige el pseudocódigo (1 min)
5. Programa en Python (15 min)
6. Ejecuta, funciona perfecto
7. **Total: 36 min, confiado y satisfecho**

**Diferencia: 109 minutos ahorrados y cero frustración.**

**Principio clave:**
> "Detectar errores temprano es exponencialmente más barato que detectarlos tarde."

Esto aplica no solo a programación, sino a ingeniería en general:
- Error en diseño: fácil de corregir
- Error en prototipo: algo costoso
- Error en producción: muy costoso
- Error en manos del cliente: desastroso

**Analogía arquitectónica:**
Encontrar un error en el plano (pruebas de escritorio) vs encontrarlo cuando la casa está medio construida (debugging de código).

**Beneficios secundarios:**

1. **Confianza:**
   - Sabés que tu algoritmo funciona antes de programar
   - No dudás de tu lógica cuando aparecen errores sintácticos en Python

2. **Comprensión profunda:**
   - Al simular la ejecución, entendés CÓMO funciona, no solo QUÉ hace
   - Esto facilita explicarlo, documentarlo, mejorarlo

3. **Prevención de lazos infinitos:**
   - Detectás antes de que tu programa se cuelgue
   - En pruebas de escritorio ves que el contador nunca cambia

4. **Validación de casos borde:**
   - ¿Qué pasa si el usuario ingresa 0?
   - ¿Y si ingresa números negativos?
   - Lo probás en papel antes de que sea un bug

**Cambio de mentalidad:**

De: "Programo y después veo si funciona" (reactivo)
A: "Verifico que funciona y después programo" (proactivo)

**Cita inspiradora:**
"Hours of debugging can save you minutes of planning." - Anónimo (irónico)

La versión correcta: "Minutes of planning can save you hours of debugging."

**Práctica profesional:**
En empresas de software serias (Google, Microsoft, etc.), el código se revisa ANTES de ejecutarse (code review). Las pruebas de escritorio son el "code review" de tu pseudocódigo.

**Transición:**
"Ahora que están convencidos de que vale la pena, veamos CÓMO se hacen las pruebas de escritorio en 4 pasos simples."

**Tono:** Motivacional pero realista. No es magia, es disciplina y método.

<!-- _header: 'Proceso' -->

# Los 4 pasos (cont.)

**Paso 3: Ejecutar paso a paso**
* Seguir cada instrucción
* Actualizar valores en la tabla
* Registrar salidas

**Paso 4: Verificar**
* ¿El resultado es correcto?
* ¿Tiene sentido?
* ¿Probar más casos?

NOTAS DEL ORADOR:
- Ser un robot. No "pensar", solo ejecutar la instrucción actual.

# Promedio de 2 números

**Pseudocódigo:**
```
LEER num1
LEER num2
suma ⟸ num1 + num2
promedio ⟸ suma / 2
MOSTRAR promedio
```

**Caso de prueba:** `num1 = 8`, `num2 = 12`

<!--
NOTAS DEL ORADOR:
- Ejemplo lineal simple.
-->

# Par o Impar

**Pseudocódigo:**
```
LEER numero
SI numero % 2 == 0 ENTONCES
    MOSTRAR "Es par"
SINO
    MOSTRAR "Es impar"
FIN_SI
```

**Probamos dos casos...**

# Suma de 1 al 5 (con lazo)

**Pseudocódigo:**
```

i ⟸ 1

    i ⟸ i + 1
FIN_MIENTRAS
MOSTRAR suma
```

<!-- _header: 'Errores comunes' -->

# Errores que detectan las pruebas

**Error 1: Lazo infinito**
* Olvidar incrementar contador
* Condición siempre verdadera

**Error 2: Off-by-one**
* Ejecutar una vez de más o de menos
* `<=` vs `<`

**Error 3: Variables no inicializadas**
* Usar variable antes de asignarle valor

<!--
NOTAS DEL ORADOR:
- Son los errores más caros de arreglar después. Baratos de arreglar ahora.
-->

<!-- _header: 'Casos de prueba' -->

# Elegir buenos casos

**Casos normales:**
* Valores típicos del problema

**Casos especiales (bordes):**
* Cero
* Números negativos
* Valores muy grandes
* Listas vacías
* Primer/último elemento

<!--
NOTAS DEL ORADOR:
- Edge cases. Ahí viven los bugs.
-->

---

<!-- _header: 'Tips' -->

# Consejos para pruebas

**Sé metódico:**
* No saltees pasos
* Actualiza todas las variables

**Usa lápiz y papel:**
* Es más fácil que hacerlo mental

**Prueba múltiples casos:**
* Un caso no es suficiente
* Especialmente para decisiones y lazos

# Pseudocódigo → Python

**Pseudocódigo:**
```
INICIO PromedioDos
    LEER num1, num2
    promedio ⟸ (num1 + num2) / 2
    MOSTRAR promedio
FIN
```

**Python:**
```python
num1 = float(input("Número 1: "))
num2 = float(input("Número 2: "))
promedio = (num1 + num2) / 2
print(f"Promedio: {promedio}")
```

<!--
NOTAS DEL ORADOR:
- La traducción es directa si el pseudocódigo es bueno.
-->
